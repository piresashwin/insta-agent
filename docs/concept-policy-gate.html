Concept · Detailed lesson · Chapter 06

Policy gate

Cognition proposes. Policy decides whether this actor may perform this action on this resource. Deny without a durable record is theater — refuse the side effect and store the deny.

  → (operator auth later — Lesson 17 / Access / IdP)

Order in routes today: policy first, then orchestrator. An edge can be in the machine and still be denied (agent + instagram.publish on an approved post). A human can pass policy and still hit 409 if the status edge is illegal.

4. The gate itself

can() is pure: role allowlist, then action-specific resource rules. No network. No LLM.

  • Agent — post.draft, media.search only (AGENT_PIPELINE principal used by agent-run)
  • Human — those plus post.approve, post.request_changes, post.start_publish, instagram.publish
  • Approve — requires human id + name
  • start_publish — post must already be approved
  • instagram.publish — agent always denied; human only from approved | media_ready | pending_upload | publishing
Hard wall

Even if status is approved, role: "agent" cannot instagram.publish. That is the irreversible-action allowlist — not a system prompt.

5. Deny is only a control if it is durable

assertAllowed calls can. On deny it calls recordPolicyDeny (creates or reuses a run, appends policy_deny, completes as needs_human), then throws ApiError 403 with run_id in the message.

A silent 403 would not pass the lesson checkpoint. The audit trail is part of the control.

7. Checkpoint (model said publish)

With the server running (pnpm --filter server dev):

curl -s -X POST localhost:3001/api/posts \
  -H 'Content-Type: application/json' -d '{"topic":"policy check"}'
# note post.id

curl -s -X POST localhost:3001/api/posts/ID/instagram-publish \
  -H 'Content-Type: application/json' -d '{"as":"agent"}'
# → 403 Policy deny: role "agent" cannot perform "instagram.publish" (run_id=N)

# → kind "policy", event type "policy_deny", status "needs_human"

8. Four notes (answered)

  1. Problem? Cognition ≠ authority. The pipeline / model cannot invent publish or approve rights.
  2. Who may call it? Every world-mutating route that matters — agent-run, approve, request-changes, publish start, published, instagram-publish. Later MCP tools must share the same assertAllowed, not invent checks.
  3. Must never? Grant instagram.publish or approve to role: "agent"; mutate on deny without logging; live only in a system prompt.
  4. Observe / test? GET /api/runs/N after a deny — kind: "policy", event policy_deny, status needs_human. Curl the matrix: agent vs human × draft vs approved.
