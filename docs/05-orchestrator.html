Week 2 · Lesson 05

Orchestrator

Source of truth for posts and lifecycle. The agent drafts; the orchestrator owns state.

Time · 1 day Control plane
Learn
  • Domain entities (posts) vs run records (runs / events)
  • Valid status transitions (status machine)
  • What belongs in orchestrator vs agent loop / skills
  • Why every status write must share one chokepoint
Build
  1. posts + statuses: draft → pending_approval → approved | changes_requested → …
  2. server/src/orchestrator.ts with transitionPost(id, next, { actor, patch })
  3. Wire agent-run, approve, request-changes, and publish stubs through that helper
  4. Agent writes draft fields only; cannot set published
Checkpoint

Illegal transitions draft → approved and draft → published return an error; GET /api/posts/:id still shows draft. DB never lies.

Built in this repo

server/src/orchestrator.ts owns VALID_TRANSITIONS and transitionPost. server/src/server.ts routes every post status change through it (including agent-run → pending_approval). Publish stubs no longer bypass the machine.

Verify (curl) 
curl -s -X POST localhost:3001/api/posts \
  -H 'Content-Type: application/json' -d '{"topic":"orch check"}'
# use returned id:
curl -s -X POST localhost:3001/api/posts/ID/approve \
  -H 'Content-Type: application/json' \
  -d '{"actor":{"id":"local-dev","name":"Local operator"}}'
# expect: Invalid transition "draft" -> "approved"

curl -s -X POST localhost:3001/api/posts/ID/published -H 'Content-Type: application/json' -d '{}'
# expect: Invalid transition "draft" -> "published"
