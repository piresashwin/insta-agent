Concept · Detailed lesson · Chapter 04

Durable runs

How we turn ephemeral console traces into an append-only database timeline — so you can reconstruct what the agent did without scrollback, and so a React monitor can exist later.

Week 1 · Lesson 04 Observability Built in this repo
One-liner

A run is one agent (or pipeline) invocation. Events are append-only facts about that invocation. Console logs are for humans in the moment; durable runs are for the system forever.

2. The problem (ephemeral vs durable)

# Ephemeral (Chapter 03 only)
[agent] step 1 tool=content_planning ...
[agent] step 1 observe ok ...
[agent] step 2 tool=finish ...
[agent] finished in 2 step(s)

# Close the terminal → gone
# React cannot read it
# You cannot compare run #1 vs run #7 next week

Durable means: assign a run_id, append each step as an event, update a small “current status” row when done. Then: 

GET /api/runs/1
→ { run: { status: "succeeded", … }, events: [ … ] }

3. Two kinds of state

KindTableChanges how?Purpose
Current state runs Updated in place (running → succeeded) Quick answer: is it done? failed?
Event log run_events Append only — never edit old rows Replay the exact tool sequence
Why append-only?

If you only store the final draft, you lose retries, bad finish attempts, and “why did this take 4 steps?”. Events are the flight recorder; the run row is the status light.

4. Schema (what we built)

4.1 runs

runs
  id, post_id?, goal, kind ('agent'|'pipeline'),
  status ('running'|'succeeded'|'failed'|'needs_human'),
  model, error?, started_at, finished_at

4.2 run_events

run_events
  id, run_id, seq, type, payload (JSON text), created_at

type examples:
  status       { status, error? }
  decision     { step, tool, thought, args }
  observation  { step, ok, tool?, data?|error?|draft? }
  error        { step?, error }

seq is 1, 2, 3… within a run so order is unambiguous even if clocks skew.

4.3 Payload compaction

Full plan JSON can be large. Helpers store a compact form for observations (field keys + short preview) so SQLite stays readable. The live agent still uses full data in memory for the next model step.

5. How it plugs into the agent loop

Chapter 03 loop gained an optional hook:

runAgent({
  goal, topic,
  onEvent: ({ type, payload }) => { … }
})

Inside the loop, after each decision / observation:

emit('decision', { step, tool, thought, args })
emit('observation', { step, ok, tool, data|error|draft })

Who calls what (same as Ch.03, plus persistence):

agent-ping.js
  createRun(...)                    → runs row status=running
  runAgent({ onEvent })             → model chooses, loop calls tools
       onEvent → appendEvent(...)   → run_events rows
  completeRun(..., 'succeeded')     → runs.status + final status event

The model still does not write to the DB. The loop still calls tools. Your script / orchestrator writes runs and events.

7. Example timeline (real shape)

After a successful 2-step agent run you get something like:

run_id=1  status=succeeded  events=6

#1 status       { status: "running" }
#2 decision     { step: 1, tool: "content_planning", args: { topic: "…" } }
#3 observation  { step: 1, ok: true, tool: "content_planning", data: { _keys: […] } }
#4 decision     { step: 2, tool: "finish", args: { draft: … } }
#5 observation  { step: 2, ok: true, tool: "finish", draft: { hook, format, … } }
#6 status       { status: "succeeded", error: null }

That is the same story as the console, reconstructed from SQLite — the Chapter 04 checkpoint.

8. API

GET /api/runs              → { runs: [ … recent … ] }
GET /api/runs?post_id=3    → runs for one post (when wired)
GET /api/runs/:id          → { run, events: [ … ordered by seq … ] }
# Try after agent:ping
curl http://localhost:3001/api/runs/1

9. How to smoke-test

  1. LM Studio up with your model.
  2. pnpm --filter server agent:ping
  3. Note run_id=N and the printed timeline.
  4. Start the API: pnpm --filter server dev
  5. curl http://localhost:3001/api/runs/N — same sequence, no terminal required.

10. What this layer must never do

  • Rewrite or delete old events (“fix” history)
  • Replace the posts table as source of truth for captions
  • Store raw secrets / API keys in payloads
  • Imply approval or publish — runs explain cognition; policy/HITL still gate the world

skill_runs (older stub table) is not the Ch.04 design. Prefer runs + run_events.

12. Four notes (answer key)

  • What problem does this layer solve? Make agent behavior inspectable after the fact and usable by a UI.
  • What is allowed to call it? Scripts / orchestrator wrapping runAgent or pipelines (createRun + onEvent).
  • What must it never do? Mutate past events; hold product approval; store secrets in the clear.
  • How do I observe and test it? agent:ping + GET /api/runs/:id — match console steps to event seq.
