Concept · Sub-chapter

Policy gates vs operator auth

Two different questions. Mixing them up produces systems that feel “approved” but are still wide open — or locked down for the wrong reason.

Authority layer Required for safe systems Pairs with Lessons 06 · 07 · 14 · 17
One-liner

Policy gates answer: Is this transition / action legal?
Operator auth answers: Who is allowed to request it?

1. Why this split exists

An agentic product has cognition (the model proposes) and authority (something decides what may happen in the world). Authority itself has two sub-questions:

Policy gateOperator auth
Question Is this action allowed given system state + rules? Is this principal allowed to ask?
Inputs Resource state, action name, actor role (agent vs human), budgets Identity (user/session/token), groups, permissions
Example allow approved + media_ready → publish is a legal transition User ashwin is an operator on this workspace
Example deny draft → published is illegal even for an admin Anonymous caller cannot hit POST /approve
Failure mode if missing Authenticated users (or the agent) can skip the lifecycle Anyone who can reach the API can approve / publish / run agents

You have a real policy gate (server/src/policy.ts — role allowlists, durable policy_deny — stacked on the orchestrator status machine (Lesson 05), and still no operator auth. Approving a post proves policy + edge allowed the request — not that a known human identity made it. Full Lesson 06 map: Policy gate (deep dive).

Order matters: authenticate first, then policy. Policy should see a real actor (user:ashwin or agent:run_abc), not “anonymous trusted localhost forever” in production.

3. Policy gates in depth

3.1 What a policy gate is

A small, boring, deterministic function (or module) that answers allow/deny before side effects. It is not a system prompt. It is not “the model promised to be careful.” 

policy.can({
  actor:  { type: "human" | "agent", id, roles },
  action: "posts.approve" | "posts.publish" | "media.fetch" | …,
  resource: { type: "post", id, status, revisionCount, accountId },
  context:  { runId, maxRevisions: 3 }
}) → { allow: boolean, reason: string }

3.2 What belongs in policy

  • Lifecycle legality — which status transitions exist
  • Role capabilities — agent may draft; only human (or approved workflow) may publish
  • Budgets — max revisions, max agent steps, rate limits per account
  • Resource scope — this operator may only act on posts for accounts they own (once multi-tenant)
  • Irreversible action lists — publish, delete, rotate secrets, disconnect OAuth

3.3 What does not belong in policy

  • Password verification / session cookies (that’s authn)
  • Creative quality (“is this caption good?”) — that’s review skills / evals / HITL judgment
  • Instagram Graph retries — that’s the IG adapter

3.4 Best practices — policy

PracticeWhy
One gateway Every mutating tool and HTTP route calls the same policy.can. No “special case” publish in MCP that skips it.
Explicit allowlist of transitions Encode VALID_TRANSITIONS; deny by default. Unknown action = deny.
Deny with a stable reason code ILLEGAL_TRANSITION, ROLE_FORBIDDEN, BUDGET_EXCEEDED — for UI, logs, and evals.
Log every deny and every irreversible allow Audit trail: actor, action, resource id, before/after status, request id.
Treat the agent as a first-class actor actor.type = "agent" with a narrow allowlist (draft, fetch media prompts). Never inherit “admin.”
Idempotency for irreversible actions Publish with an idempotency key so retries don’t double-post even when policy allows twice.
Unit-test the matrix Table-driven tests: (status, action, actor) → allow/deny. This is a policy eval.
Keep policy pure No network calls inside can(). Pass state in; return decision out. Easy to test and reason about.

4. Operator auth in depth

4.1 Authn vs authz (inside “operator auth”)

  • Authentication (authn) — prove identity: “this request is Ashwin.”
  • Authorization (authz) — grant rights: “Ashwin may operate workspace X.”

People say “auth” for both. In design docs, keep them separate. Policy gates often consume the result of authz (roles) but do not replace login.

4.2 What operator auth protects

  • Dashboard routes (approve, settings, connect Instagram)
  • Orchestrator HTTP API
  • Optionally MCP: shared secret, OAuth for remote MCP, or local-only stdio (stdio MCP is already “whoever runs the process”)

4.3 Best practices — operator auth

PracticeWhy
Never expose the API without a gate in prod Localhost-only is fine for learning. Public URL without auth = anyone can publish with your tokens.
Prefer a battle-tested identity layer early Options: Cloudflare Access in front of the app, Auth.js / Clerk / WorkOS, or Meta/Google OAuth for operators. Don’t invent crypto sessions on day one.
Short-lived credentials Session cookies (HttpOnly, Secure, SameSite) or short JWTs with refresh. Rotate on logout.
Bind actions to a stable user id Store approved_by, requested_by on iterations — audit needs a person, not “UI.”
Least privilege roles e.g. viewer (read queue), editor (request changes), publisher (approve + publish), admin (OAuth + secrets).
Separate operator identity from Instagram identity Logging into the dashboard ≠ connecting an IG Business account. Different OAuth apps / token stores.
Defense in depth for MCP Local stdio: OK for single-user machines. Remote MCP: require auth. Still run tool calls through policy.
Rate-limit authenticated routes Auth stops strangers; it doesn’t stop a stolen session from spamming publish.

4.4 Practical implementation paths (pick by stage)

Learning / local (now)

  • Bind API to 127.0.0.1
  • Optional shared OPERATOR_TOKEN header for non-browser clients
  • Document: “not internet-safe”

Single-operator prod (simple)

  • Cloudflare Access (email allowlist) in front of UI + API
  • Or HTTP Basic behind TLS (acceptable only for tiny personal tools)
  • Pass CF Access identity headers into orchestrator as actor

Multi-user product

  • Proper IdP (OIDC) + sessions
  • Workspace membership table
  • RBAC mapped into policy.can roles

Agent / MCP callers

  • Issue a scoped API token per harness (agent:cursor)
  • Token role = agent allowlist only
  • Never give harness tokens the publisher role

5. How they work together (worked example)

Scenario: Someone calls POST /api/posts/:id/publish.

  1. Operator auth: No session → 401 Unauthorized. Stop.
  2. Operator authz: User is viewer only → 403 Forbidden. Stop.
  3. Policy: User is publisher, but post status is draft → 409 / ILLEGAL_TRANSITION. Stop.
  4. Policy: Status is approved + media ready → allow.
  5. Adapter: Graph publish with idempotency key; on success set published; write audit row ashwin published post_123.

Same call from the agent with a valid agent token still dies at step 3/role: agent role cannot posts.publish, regardless of status.

6. Common mistakes

MistakeWhy it hurts
“We have approve buttons, so we’re secure.” Buttons without operator auth are UI theater on an open API.
“We put Cloudflare Access on the UI only.” Attackers hit the API directly. Protect both or make the API private.
“The system prompt says never publish.” Not a control. Policy + auth are controls.
“Admin bypasses the status machine.” Breaks invariants and evals; break-glass should be explicit, logged, rare.
“MCP and HTTP have different publish rules.” Harness shopping for the weak door. One policy module.
Storing Instagram tokens as “the user session.” Confuses product login with platform OAuth; nightmare to revoke correctly.

8. Checkpoint

You understand this chapter when you can say
  1. Policy without auth → legal transitions callable by strangers.
  2. Auth without policy → known users can still skip the lifecycle / publish drafts.
  3. Safe systems require both, plus an audit log that records who and whether it was legal.

  • Write one deny reason that is only auth (401/403) and one that is only policy (ILLEGAL_TRANSITION).
  • Pick your stage (local / single-operator / multi-user) and name the auth approach you’ll use before public deploy.
Suggested allow/never (updated)

The LLM may draft structured content via skills. It may never publish or approve. Humans may approve/publish only when authenticated and the policy transition is legal. Until operator auth exists, the API stays localhost-only.
