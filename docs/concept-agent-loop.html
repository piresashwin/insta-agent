The agent loop

Full explanation of ReAct-lite cognition: how a model repeatedly chooses tools, observes results, and stops under budgets — and how that differs from the fixed skill pipeline you already smoke-tested.

Week 1 · Lesson 03 LangChain skills as tools No LangGraph required yet
One-liner

An agent loop is a budgeted decide → act → observe cycle. Skills (Chapter 02) are the tools. The loop is who picks the next tool. The orchestrator and policy (later) still own the real world.

2. Pipeline vs agent loop (the core distinction)

2.1 Fixed pipeline (what you smoke-tested)

runContentPipeline(topic):
  plan    = planContent(topic)           # always 1st
  caption = writeCaption(plan)           # always 2nd
  media   = generateMediaPrompts(...)    # always 3rd
  review  = reviewPost(...)              # always 4th
  return merge(...)

Pros: predictable latency, easy to debug, good default for Instagram drafts.
Cons: cannot skip, reorder, or retry one step without you changing code.

2.2 Agent loop (ReAct lite)

runAgent(goal):
  history = [system, user(goal)]
  loop while under budget:
    decision = model.chooseTool(history)   # { tool, args }
    result   = execute(decision)
    history.append(observation(result))
    if decision.tool == "finish":
      return decision.args.draft
  fail loudly (max steps / timeout)

Pros: adaptive — retry plan, skip optional steps, react to errors.
Cons: can wander; must have step/time budgets; harder to test.

Use a pipeline when…

  • The path is known (your IG post production)
  • You want stable demos and evals
  • Latency must be bounded tightly

Use a loop when…

  • The model must decide among tools
  • Recovery/retry paths vary
  • You’re learning “agentic” behavior
Product advice for this repo

Keep the pipeline as the default agent-run path for reliable drafts. Build the loop as a parallel learning runtime (and later an optional mode). Do not throw away the pipeline to “be more agentic.”

3. ReAct in plain language

ReAct = Reason + Act. The model does not only answer in prose. It repeatedly:

  1. Reasons about the goal and what it has seen so far
  2. Acts by calling a named tool with arguments
  3. Observes the tool’s return value
  4. Repeats until it calls a special stop tool (finish) or hits a budget

In our design, “reason” is usually implicit inside a structured decision (JSON: which tool + args), not a long chain-of-thought essay you have to parse. That matches Chapter 02: contracts over vibes.

4. What is a tool?

A tool is a named capability the agent is allowed to call — with clear inputs and outputs — so it can do something instead of only writing text.

One line: tool = function the model can invoke by name (usually with a schema), then see the result.

4.1 Skill vs tool vs model vs side effect

TermMeaningYour example
Skill Domain capability you authored planContent in content-planning.js
Tool That capability registered for the agent loop under a name content_planning → calls planContent
Model Chooses which tool / writes structured JSON Gemma via createModel
Side effect / API Real world (IG publish) — not a free agent tool without policy Graph publish

Rule: skill is the implementation; tool is how the loop exposes it.

4.2 Shape of a tool

name:  content_planning
args:  { topic: string }           ← contract (Zod / JSON schema)
run:   planContent(args)           ← your code
out:   { hook, angle, format, … }  ← observation back to the model

# Special stop tool (Chapter 03):
name:  finish
args:  { draft: object }
run:   stop the loop and return the draft

Without tools, the model can only talk. With tools, it can act, observe, then decide again.

4.3 Good tools (examples)

ToolContractWhy it’s good
content_planning { topic } → plan JSON One job, clear schema, pure (no DB/IG)
caption_writing { hook, angle, format } → caption JSON Small, typed, no side effects
media_search (later) { query } → candidate URLs/licenses Returns data; download/publish stay behind policy
finish { draft } → stop Explicit stop — better than hoping the model says “I’m done”

4.4 Bad tools (examples)

ToolWhy it’s bad
do_everything_for_instagram({ topic }) → “ok I posted it” God-tool: plans + writes + uploads + publishes; bypasses approval; untestable
publish_now exposed directly to the agent Irreversible side effect with no policy/HITL; model can call it when confused
run_sql({ query }) Unbounded power; one bad string wrecks source of truth
ask_model_unstructured({ prompt }) → free-form string No contract — forces regex parsing; breaks reliable observations
maybe_plan_or_publish({ vibe: "viral" }) No schema, no single job; output shape unpredictable

4.5 Quick test: is this tool good?

QuestionGoodBad
One clear job? Yes “Handle the post”
Typed in/out? Zod / JSON Free text
Side effects? None, or tightly gated Publish / delete / email
Safe if called twice? Mostly yes Double-posts
Callable from tests without IG? Yes Needs live credentials
Rule of thumb

Good tools return artifacts or lookups. Bad tools mutate the world or return mush. If the agent can call it by name and get a structured result back into the loop, it’s a tool — design that surface carefully.

4.6 How does anything know a tool’s parameters?

Simple answer: nothing magically introspects the tools. We tell the model in the prompt; the tool code enforces args when it runs.

Note: in Chapter 03 this is the agent loop (runAgent), not Express. server.js still uses the fixed pipeline by default and does not yet know tool parameters.

WhoHow they “know” parameters
Model Reads TOOL_DESCRIPTIONS text pasted into the system prompt (e.g. args: { topic: string })
Tool function Hard-coded checks / Zod when called (e.g. require args.topic, parse draft)
Express orchestrator Does not — not wired to the loop yet 
# 1) YOU write descriptions
TOOL_DESCRIPTIONS.content_planning =
  "… args: { topic: string }. Returns hook, angle, …"

# 2) Loop puts them in the prompt → MODEL returns JSON
{ "tool": "content_planning", "args": { "topic": "5-minute morning routine" } }

# 3) Tool validates when it runs
if !args.topic: throw "content_planning requires args.topic"

One sentence: the loop doesn’t discover APIs like a database — you describe args in the prompt; the tool code enforces them when called. (Same idea as ChatGPT function calling.)

4.7 Who calls the tools, and how?

Your Node code calls the tools — not the LLM. The model only chooses. The loop executes.

WhoJob
Model (e.g. Gemma) Returns JSON: next tool name + args
runAgent (loop.js) Reads that choice, then calls the JS function
Tool function Does the work (planContent, or validate finish) 
1. loop builds prompt (tools + goal + history)
2. loop asks model → gets { tool, args }
3. loop runs:  tools[decision.tool](decision.args)   ← real function call
4. loop saves result in history
5. repeat until finish or budget

In code that is literally:

const fn = tools[decision.tool];          // e.g. tools["content_planning"]
const data = await fn(decision.args);     // → runContentPlanning → planContent

Analogy: model = customer pointing at a menu item; loop = waiter; tool = kitchen. The customer doesn’t cook.

Who starts it today? You, via agent:ping → runAgent({ goal, topic }). Later Express or MCP can call runAgent the same way — still the loop calls tools; the model only chooses.

5. Anatomy of the loop

5.1 Goal

A short natural-language objective, e.g. “Draft an Instagram reel concept about a 5-minute morning routine.” The loop does not own brand files or DB rows; the caller may inject brand text into the goal/system prompt.

5.2 Tool registry

A map from tool name → function. Chapter 03’s minimal registry (on purpose, so you can see choices clearly): 

tools = {
  content_planning: (args) => planContent(args),
  // returns Zod-validated plan: hook, angle, format, …

  finish: (args) => {
    // args.draft = final artifact the agent claims is done
    return { done: true, draft: args.draft }
  }
}

Later you can register caption_writing, image_reel_generation, post_review the same way — each already a pure structured skill.

Rule: every tool returns data. None of them publish to Instagram or flip posts.status to published.

5.3 Decision step (model as router)

DecisionSchema = {
  tool: "content_planning" | "finish",
  args: object,           # tool-specific
  thought: string?        # optional short rationale for logs
}

decision = createStructuredModel(DecisionSchema).invoke("""
  Goal: {goal}
  History of observations: {history}
  Available tools: {toolDescriptions}
  Choose exactly one next tool.
""")

Same LM Studio path as Chapter 02 (promptJson + Zod). The model is not free-form chatting with the user here — it is emitting a machine decision.

5.4 Act + observe

if decision.tool not in tools:
  observation = { ok: false, error: "unknown tool" }
else if decision.tool == "finish":
  return decision.args.draft   # success stop
else:
  try:
    data = tools[decision.tool](decision.args)
    observation = { ok: true, tool: decision.tool, data }
  catch err:
    observation = { ok: false, tool: decision.tool, error: err.message }

history.append(observation)
# normalize: keep observations compact JSON, not megabyte dumps

5.5 Stop conditions

StopMeaningCaller should…
finish tool Success — draft ready Hand draft to orchestrator
Max steps Model never finished Fail loud (no fake draft)
Timeout Wall clock exceeded Fail loud
Repeated tool errors Optional policy Escalate / fail

6. Budgets are architecture

Without budgets, “agentic” means “might run forever.” Budgets are not polish — they are how you keep cognition safe on a laptop GPU and in production. 

MAX_STEPS   = 8          # course default
TIMEOUT_MS  = 60_000     # wall clock for the whole loop
# later: max tokens / max $ per run
BudgetFailure mode if missing
Max steps Infinite content_planning spam
Timeout Hung local model blocks the process
Token/cost (later) Cloud bill or LM Studio thrash
Same ethos as Chapter 01

Hitting a budget is a clear failure, not a trigger to invent canned Instagram copy. Fake success teaches the wrong lesson.

7. Full pseudo code (minimal Ch.03 agent)

function runAgent({ goal, maxSteps = 8, timeoutMs = 60_000 }):
  started = now()
  history = []
  tools = {
    content_planning: (args) => planContent(args),
    finish: null   # handled specially
  }

  system = """
    You are a drafting agent for Instagram concepts.
    Tools:
      - content_planning({ topic }): produce hook/angle/format/…
      - finish({ draft }): end the run with the final draft object
    Prefer calling content_planning once, then finish with a draft
    built from that plan. Do not invent tools.
  """

  for step in 1 .. maxSteps:
    if now() - started > timeoutMs:
      throw Error("Agent timeout")

    decision = chooseTool(system, goal, history)  # structured
    log("step", step, decision.tool, decision.args)

    if decision.tool == "finish":
      validateDraft(decision.args.draft)  # optional Zod
      return { ok: true, draft: decision.args.draft, steps: step }

    if decision.tool not in tools or decision.tool == "finish":
      history.push({ ok: false, error: "unknown or invalid tool" })
      continue

    try:
      data = tools[decision.tool](decision.args)
      history.push({ ok: true, tool: decision.tool, data })
    catch err:
      history.push({ ok: false, tool: decision.tool, error: err.message })

  throw Error("Agent exceeded MAX_STEPS without finish")

8. Example trace (what you should see)

goal: "Draft an IG reel about a 5-minute morning routine"

step 1  tool=content_planning  args={ topic: "5-minute morning routine" }
        observe ok: { hook: "…", format: "reel", alt_hooks: [...] }

step 2  tool=finish  args={ draft: { hook, angle, format, … } }
        → return draft

# Bad trace (hits budget):
step 1  content_planning …
step 2  content_planning …   # model stuck retrying
…
step 8  content_planning …
→ Error: Agent exceeded MAX_STEPS without finish

Printing each step is the Chapter 03 form of observability. Chapter 04 will write those steps into run_events instead of only the console.

9. What the loop must never do

  • Call Instagram Graph / publish
  • Mark a post approved or published
  • Store OAuth secrets
  • Bypass policy “because the model said so”
  • Swallow errors and return canned captions by default

Killing the process mid-loop must leave the database untouched (Chapter 03 checkpoint) — no world side effects yet.

See Policy vs operator auth: the loop is cognition; legality and identity are authority.

13. Four notes (answer key)

  • What problem does this layer solve? Adaptive multi-step progress toward a goal when the next action is not hardcoded.
  • What is allowed to call it? Orchestrator, local scripts, later MCP — with the same tool purity rules.
  • What must it never do? Irreversible world actions; run without budgets; fake success on failure.
  • How do I observe and test it? Step logs now; durable run_events in Chapter 04; force budget failures on purpose.
